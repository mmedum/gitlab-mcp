# Security review — v4.0.0

Range: `v3.0.0` to the release commit, on `release/v4.0.0`. Reviewed on
2026-10-23. The release commit itself changes only the CHANGELOG, the
documents and this file.

**Result: no finding at confidence 8 or above.** Two low findings,
recorded in §16a: `update_issue` still sent `confidential: false` for
an issue its read showed public, fixed in 65c44f1; and
`rerequest_review` checks for an approval at read time, not in the
request GitLab acts on, which §7.3 now says.

- **The module path** (8d7c08e): no finding. 175 files, 414 lines each
  way, identical once `gitlab-mcp/v3` and `gitlab-mcp/v4` are read as
  one. The one extra line is the CHANGELOG's `**Breaking:**` entry.
  `.goreleaser.yaml`, the `Makefile`, `go.mod`, the README and the gate
  testdata are among the files. No `gitlab-mcp/v3` remains outside
  `CHANGELOG.md` and `audit/`.
- **`make_issue_public`** (a6d2b0c; `internal/tools/ship.go`
  `makeIssuePublic`; `internal/service/write_items.go` `UpdateIssue`,
  `MakeIssuePublic`, `updateIssue`; `internal/tools/register.go` `gate`,
  `handle`): no finding.
  - It is Destructive with no toolset. `gate` registers it only with
    `GITLAB_MCP_ENABLE_DESTRUCTIVE=true`, and never under read-only.
    `handle` refuses a call without `confirm: true`, a dry run aside. The
    service checks no flag itself: registration is the control, as rule
    6 asks. `TestGate` holds `gate` by kind: read-only beats both flags,
    and a Destructive tool needs its own flag, not the Ship flag.
  - It goes through `writeTarget`, so the write allow-list holds, and
    through the `updated_at` witness. It sends only `confidential:
    false`. On an issue the read shows public it sends nothing and says
    so. The dry run returns before the `PUT`, and rule 14's client
    refuses a write under that context anyway.
  - `update_issue` refuses `confidential: false` on an issue the read
    shows confidential, whatever the flags, after the witness and before
    the dry run. Only `MakeIssuePublic` sets `publish`. No other write
    sends `confidential` to an existing issue: `create_issue` sends it
    only as `true`, the quick-action guard refuses `/confidential` in a
    body, and `move_issue` still refuses a wider project.
  - **Low: `update_issue` still sends `confidential: false` for an issue
    its read shows public.** If another person makes the issue
    confidential between that read and the `PUT`, the `PUT` makes it
    public again. This predates the range; 3.0.0 had the same window with
    the Ship flag off. The window is the one §4.6 accepts for every
    read-compared witness. Using it takes another person's change in
    that window and a call asking for `confidential: false` on a public
    issue. Recommendation: drop `confidential: false` from the body when
    the read shows the issue public, as `make_issue_public` already does,
    so `update_issue` never sends it. No input changes, so this breaks
    nothing. Fixed in 65c44f1, with a test that nothing is sent.
- **`anthropic/requiresUserInteraction`** (a6d2b0c;
  `internal/tools/register.go` `add`; `internal/tools/features.go`
  `deleteLabel`, `deleteMilestone`): no finding. `add` panics when a tool
  that is not Destructive sets `PromptEveryCall`. The tool's `_meta` is
  built once, so the quick-action key and the prompt key cannot replace
  each other. The full-surface dump lists 105 tools: 22 with
  `destructiveHint`, and exactly `delete_label`, `delete_milestone` and
  `make_issue_public` with the mark. The mark adds a client prompt and
  removes no control.
- **`rerequest_review`** (4e3dd85, 2f0c5e1; `internal/service/rereview.go`
  `RerequestReview`, `settleRereview`, `reviewer`;
  `internal/gapi/graphql.go` `mutate`, `RereviewMergeRequest`;
  `internal/tools/writes.go` `rerequestReview`): no finding beyond the
  low one below.
  - It is Write, so it is absent under read-only, and a `read_api` token
    could not run the mutation anyway. It goes through `writeTarget`, so
    the allow-list holds. `username` and `reviewer_state` are never
    sent: the mutation carries the project's path from this call's own
    project read, the number formatted from an integer, and the user's
    id from GitLab's reviewer listing. `bodies` lists both inputs as
    plain fields with that reason.
  - The mutation is the constant `rereviewMutation`. Every value goes in
    `variables`, encoded with `encoding/json`, so no input reaches the
    query text. There is no raw GraphQL tool. The `graphqlops` part of
    `api-coverage` refuses a `Call` to `api/graphql` outside `mutate` and
    holds each operation against §8a.
  - An approval is refused `[blocked]` if either the reviewer's state is
    `approved` or GitLab's approvals list names them, both read before
    the mutation, and usernames compare case-insensitively.
    `MergeRequests::RequestReviewService` removes only that reviewer's
    own approval, so no one else's is at stake. A reviewer still
    `unreviewed` is refused, so `unreviewed` read afterward can only
    mean the re-request landed. The dry run returns before the `POST`.
  - A lost answer is never resent: the `POST` is not repeatable, and
    `settleRereview` reads the reviewer's state to settle it. When the
    payload is there it is read first, so a mutation that ran is never
    reported as refused. A refusal that GitLab words as missing or
    forbidden is `[not_found]` with the server's own text. Any other
    top-level error in a 200 answer is `[unexpected]`, and GitLab's text
    is not quoted.
  - **Low: the approval check is made at read time, not by GitLab.**
    The mutation takes no witness. If the reviewer approves between the
    read and the mutation, GitLab removes that approval. Only the
    reviewer can open that window, GitLab writes a system note, and the
    reviewer is notified and asked to review again. No change is
    recommended beyond saying, in §7.3, that the check is a read.
- **The GraphQL path through the client** (9e6f45c;
  `internal/gapi/client.go` `prepare`, `send`, `reauthorize`,
  `followMove`, `movedTo`, `endpoint`, `attempt`;
  `internal/gapi/call.go` `RootWeb`, `isWrite`): no finding.
  - `RootWeb` resolves `api/graphql` against the instance's web base.
    `attempt` checks the origin before it attaches the token, so the
    token goes only to the instance that issued it.
  - No redirect is followed. `CheckRedirect` returns the response, and
    `movedTo` re-requests only a `GET` under `RootAPI`. A redirect on
    `api/graphql` is `[unexpected]`.
  - `isWrite` counts the `POST` as a write, so a dry run refuses it in
    `prepare` before the network. A 5xx or a lost answer is
    `[ambiguous_outcome]`, never retried. Only a 429, which GitLab sends
    before the controller runs, and a connection that was never made
    are retried.
- **GraphQL errors in `classify.go`** (9e6f45c;
  `internal/gapi/classify.go` `parseEnvelope`, `invalidToken`,
  `refused`, `envelope.detail`): no finding.
  - A 401 with `{"errors":[{"message":"Invalid token"}]}` is now
    `[auth]` with `reauth` set. `send` reauthorizes once per call.
    `reauthorize` drops the refused token and, since the `POST` is not
    repeatable, returns without a new attempt. The mutation is not
    replayed, the call does not loop, and the next call refreshes under
    the existing lock (rule 12). Only a gitlab.com answer can produce the
    message; no content reaches it.
  - The new branch is read only when the body has no `message` key. For
    REST, a body with an `errors` array of objects now has its text
    quoted, cut to 300 characters by `detail`, in the tool's error. That
    text is GitLab's own error text and goes to the model, not to a log.
    `handle` logs the tool, the outcome and the duration, and
    `logAttempt` the call name, status and bucket. Neither logs an
    error's message (rule 3).
