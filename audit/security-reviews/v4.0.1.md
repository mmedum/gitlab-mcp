# Security review — v4.0.1

Range: `v4.0.0` to the release commit, on `release/v4.0.1`. Reviewed
on 2026-10-23.

**Result: no finding.** The range holds one production change, its test
and the in-memory GitLab's answer.

- **Blob search rows** (`internal/gitlab/gitlab.go` `SearchBlob`;
  `internal/gapi/planning.go` `SearchBlobs`; `internal/service/planning.go`
  `Search`, `blobRow`). A blobs or wiki blobs search decodes into its own
  type, so a row whose `id` is the blob's SHA no longer fails the whole
  answer (§18 row 129).
  - `SearchBlob` reads fewer fields than `SearchHit` did for these
    scopes: `id` is not read at all, so nothing new reaches the model or
    a log.
  - The excerpt still passes `render.Code` and the excerpt budget, and
    is rendered inside the untrusted-content boundary (rule 4). A match
    by name sends up to 1024 bytes of the file from line 1; it is cut by
    the same budget.
  - `SearchBlobs` uses the same three `Call` literals as the other two
    search methods: the same paths, the same query, `Name: "search"`, the
    same redirect and pagination rules and the same `advancedSearch`
    refusal. The api-coverage rows name it.
  - The class vocabulary is unchanged.
- **Tests only:** the in-memory GitLab answers a match by name first,
  with the blob's SHA as `id`, as GitLab's `FileFinder` does. Every path
  and content is the fixture's own.
- **Release checks run:** `make check`; `make vuln` at `v4.0.0` (no
  vulnerabilities); `deps`, `schema-refetch` (both vendored schemas
  unchanged upstream) and `leaks-history`; `schema-diff` (no change
  against v4.0.0); a live run on gitlab.com whose search by a file's name
  returned that file, transcript read.
