# Security review — v2.2.0

Range: `v2.1.0` to the release commit, on `main`. Reviewed on
2026-10-02.

**Result: no open finding at confidence 8 or above.** One finding at
confidence 8, in `apply_suggestions`'s refusal of invisible characters,
fixed before the release (#45). Five low findings recorded below.

- **Applying suggestions** (#42): one finding, confidence 8, fixed in #45.
  `render.Invisible` (`internal/render/sanitize.go:109`), the check
  `ApplySuggestions` runs on each suggestion's text before asking
  (`internal/service/ship.go:1051`), refuses `hidden`, controls,
  U+2800, U+3164 and U+FFA0, but not U+115F or U+1160, the other Hangul
  fillers. Like U+3164 they are default-ignorable and drawn as nothing,
  and they are letters (Lo): Node and Python accept `const <U+115F> = 1`
  and `'<U+115F>'.isidentifier()`. That is the invisible-identifier
  backdoor U+3164 was added to stop (`const { timeout,<U+115F>} = req.query`)
  with the character swapped. `Code` does not write U+115F out either, so
  `list_discussions` shows it raw, and the question shows it raw inside
  its code span (`quoted` keeps it). Variation selectors (U+FE00 to
  U+FE0F, U+E0100 to U+E01EF), U+034F and U+17B4 to U+17B5 also pass. They
  are identifier characters (Mn) after the first, so `ok` and `ok<U+FE00>` read
  the same and name different variables. The check reads the text as
  written. Anyone who may comment on the merge request can write a
  suggestion, so the commit under the person's name holds code that
  reads otherwise than it runs, the outcome §4.12 asks the person to
  prevent. Confirmed by running `Invisible`, `Code` and `Line` on each
  character. Fixed: `Invisible` also takes Unicode's
  `Other_Default_Ignorable_Code_Point` and `Variation_Selector` sets, so
  every Hangul filler, U+034F, U+17B4 to U+17B5 and every variation
  selector is refused and named. Examined and holding: every id is found on the merge request
  named before anything is sent, so an id from another project cannot be
  applied. The source branch is held to `create_commit`'s rule, and a
  fork's branch is read in the fork, which is held to the write
  allow-list. An id stands for the text it was read with, because an edit
  gives a comment new suggestion ids (§18 row 110). The question binds
  the whole head, the source branch, and each id with a hash of its whole
  text, and the arguments hash binds the ids and `commit_message`. The
  verified retry reads again, so a push, an edited comment or a sixth
  suggestion changed during the question is refused rather than
  committed. Suggestions past the fifth are counted in the question, and
  a text past 300 characters is shown cut with the count of the rest. The
  PUT is `Once`. A lost answer is settled by reading the suggestions and
  the branch: anything short of every one applied is unknown, and nothing
  is applied again. A dry run never asks.
- **Low, the question's rendering of code** (confidence 5): `quoted`
  folds a suggestion onto one line, collapsing line breaks and
  indentation. It also turns `"` and backticks into `'` and `//` into
  `/[/]`. §4.12.5 says it does, and the person is asked with that
  rendering. For code, though, the question's closing line, "quoted as
  written", claims more than it shows. A dedent that moves a statement
  out of a block in Python or YAML, or `"$x"` against `'$x'` in shell,
  reads the same in the question. Only the person reading the question
  and nothing else is misled. `list_discussions` has the exact text.
- **Low, the refusal's pointer** (confidence 4): a suggestion refused for
  U+3164, U+2800, U+FFA0 or a control character is said to be "in
  list_discussions" with them written out. `Code` writes out only
  `hidden` characters, so those four classes are shown raw there. The
  refusal still holds.
- **Low, the commit message** (confidence 3): `commit_message` is the
  model's and is not in the question. It is bound by the arguments
  hash and runs no quick action (§18 row 110). A persuaded model can
  word the commit made under the person's name, as it can with
  `create_commit`.
- **Low, a settle's attribution** (confidence 2): `madeByThisCall`
  compares the head's author name with the account's display name. Both
  outcomes report the suggestions landed and say not to apply again, so
  only the "by this account" wording can be wrong.
- **Canceling an auto-merge** (#42): no finding. Ship-gated and held to
  the allow-list. Nothing is sent when no auto-merge is set, the merge
  request is locked or it has merged. The outcome comes from GitLab's
  body and a read afterwards, never the status alone. A repeat is safe
  (§18 row 109). It does not ask, as §4.12.4 decides.
- **Draft review comments** (#43): one low finding (confidence 3). After
  a 204, `publish_review_comment` reports the draft lost unless it finds
  a comment by the account, newer than the mark, with the draft's text
  and at the draft's paths and lines. A published comment that GitLab
  placed or stored otherwise would read as lost, and the result says
  `add_review_comment` adds it again, which would post it twice. No case
  where GitLab does so was confirmed. Examined and holding:
  `update_review_comment`'s body goes through the quick-action guard
  (`Guarded`). `publish_review_comment` refuses a draft with a
  quick-action line, and `submit_review` refuses one in any draft.
  GitLab's draft list is unpaged (the pinned snapshot gives it no page
  parameters), so no draft is unchecked. GitLab shows only the account's
  own drafts, so the window between that read and the publish is the
  account's alone. `note_sha256` is compared with a fresh read, and the
  hash is never sent. The draft's own position is sent back, and a draft
  on an image is refused. The publish is `Once`, and a lost answer is
  settled by the draft and the threads. The second-reply `[conflict]`
  reads GitLab's validation text only to classify it.
- **Reactions** (#40): no finding. The emoji name is checked against
  `[a-z0-9_+-]{1,100}` and sent in the body, never the path. The project,
  iid, note and award ids go through `segment` and `idArg`. `react` is
  Write, held to the allow-list, and its POST is never repeated: a lost
  answer is settled by the account's reactions before and after. GitLab's
  404 text is quoted as GitLab's. Emoji names shown are GitLab-validated
  and written through `Ident`. Vote counts are integers.
- **Versions, reviewer states and git names** (#41): one low finding
  (confidence 4). `search` with scope `commits` still prints the author
  name outside the markers (`internal/render/planning.go:300`). It is
  folded to one line, as §4.1.2 allows, but #41 moved the same name
  inside the markers everywhere else, and the line comes after the
  boundary notice. That code predates the range. Examined and holding:
  `get_commit`, `get_blame`, `list_commits`, `list_mr_commits` and
  `compare_refs` carry author and committer names inside the markers.
  Version ids are only matched against GitLab's list and never reach a
  URL. The compared heads are GitLab's shas, sent as query values.
  Reviewer usernames and states are written through `Ident`. All of it is
  Read.
- **Gating**: no finding. `apply_suggestions` and `cancel_auto_merge`
  are Ship. `react`, `update_review_comment` and `publish_review_comment`
  are Write. Each resolves its target through `writeTarget`, and
  `scripts/gates bodies` names the two new plain inputs with a reason.
