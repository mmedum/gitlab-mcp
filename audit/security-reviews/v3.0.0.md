# Security review — v3.0.0

Range: `v2.4.0` to the release commit, on `release/v3.0.0`. Reviewed on
2026-10-22. The release commit itself changes only the CHANGELOG, the
documents and this file.

**Result: no finding at confidence 8 or above.** One low finding,
recorded in §16a: `apply_suggestions`' witness covers the text a
suggestion puts in, not the lines it replaces.

- **The module path** (d91c0cd): no finding. 173 files, 418 lines each
  way, every changed line naming the module path, `.goreleaser.yaml`,
  the `Makefile`, `go.mod` and the gate testdata included. No
  `gitlab-mcp/v2` remains outside `CHANGELOG.md` and `audit/`.
- **Merge request dependencies** (652bb0d; `internal/service/features.go`
  `dependencyTargets`, `findDependency`, `LinkMergeRequests`,
  `UnlinkMergeRequests`; `internal/gapi/features.go`;
  `internal/tools/features.go`): no finding.
  - Both projects go through `writeTarget`, so the write allow-list and
    the project read hold for each side. Every request uses the numeric
    project id from that read and `idArg` for each number; the block id
    a `DELETE` uses comes from GitLab's listing, never from input. A
    merge request linked to itself is refused `[invalid]`.
  - On both tools the dry run returns after the read and before the
    `POST` or `DELETE`, and rule 14's client refuses a write under that
    context anyway.
  - The create is sent once; a lost answer goes to `settle`, which
    reads. A read cut at `maxDependencyPages` reports unknown, never
    not created, and unlink refuses `[unsupported]` rather than call a
    cut read absent.
  - Both tools are Write and absent under read-only. On Premium a
    dependency holds a merge; adding one is reversible, and removing one
    can only release a merge someone already set to auto-merge, which
    other Write tools can already do. On Free nothing is held (§18 row
    122). Not a Ship bypass.
  - GitLab refuses a create without read access to the other merge
    request, and the result carries only the input numbers and the
    project refs `writeTarget` resolved.
- **Dependencies in `get_merge_request`** (`internal/service/items.go`
  `dependencies`; `internal/render/text.go` `dependencyList`,
  `linkedItem`): no finding. A merge request the account cannot read is
  dropped by GitLab's entity (row 122); the server counts the row as
  `hidden` and shows nothing else of it. Titles go through `render.Line`
  and `bd.Inline`; reference, state and URL through `Ident`; the URL is
  shown, never called. A soft error gives null, an auth or rate-limit
  error fails the read, and a read with an offset skips the lists.
- **The question's removal** (a24ddd4; `internal/tools/register.go`,
  `tools.go`; `internal/service/*.go`): no finding; everything that
  stays still holds.
  - `register` still panics on a Destructive tool without `confirm` and
    on a write without `dry_run`. `handle` refuses a Destructive call
    without `confirm: true` before the quick-action guard and the
    handler, a dry run aside, and the guard still runs before the
    handler.
  - `allowed` and `gate` are unchanged and no tool changed kind or
    toolset. The full-surface dump lists 103 tools, none with
    `anthropic/requiresUserInteraction`; `destructiveHint` is true on
    all 21 Ship and Destructive tools.
  - Each removed `ask` came after the dry-run return and the last check
    and before the write, so every read, witness and refusal ahead of
    it stays. Read for merge, approve, apply, `play_job`,
    `create_release`, `create_tag` (the protected-tag rule still
    refuses `[blocked]`), the seven deletes, `upload_file` (still held
    by `writeTarget` and the upload directories) and `update_issue`
    (making a confidential issue public still needs
    `GITLAB_MCP_ENABLE_SHIP`, before the dry run).
  - The refusal of a call carrying `requestState` or `inputResponses`
    protected only the question, and nothing reads those fields now.
    `AskFailures` covered only calls that asked; every other write is
    classified in `gapi.classifyTransport`, as before.
  - No new log line; the startup log drops `require_prompt`.
- **`apply_suggestions`' witness** (`internal/service/ship.go`
  `ApplySuggestions`, `sameSuggestion`; `internal/render/sanitize.go`
  `SuggestionText`, `Invisible`): one low finding.
  - Per suggestion, `Invisible` refuses `[blocked]`, a text shown cut
    refuses `[unsupported]`, and a different text refuses `[stale]`, all
    before the dry run and the `PUT`. Each text is held against its own
    id's suggestion and is never sent; only ids go to GitLab. `text` is
    required in each item.
  - `Invisible` refuses every rune `Code` would write out, and decoded
    JSON is valid UTF-8, so the shown text is GitLab's `to_content`
    byte for byte unless cut. The cut is the same 2,000-rune one
    `list_discussions` uses: a text equal to the first 2,000 characters
    is refused, and 2,000 exactly is accepted.
  - The only normalization is CRLF to LF and trailing newlines, so
    indentation is exact; only blank lines at the end can differ.
  - GitLab gives an edited comment's suggestions new ids and refuses an
    outdated one, and `suggestionsOn` holds each id to this merge
    request.
  - **Low: the witness covers what is put in, not what is taken out.** A
    commenter's `suggestion:-12+0` with one plausible line replaces
    thirteen; a client's prompt shows `{id, text}`, the one line, where
    the 2.x question named the file and the range. The Ship flag must be
    on, default and protected source branches are refused,
    `list_discussions` shows the model the range and the replaced text,
    and the commit lands on the source branch for review before merge.
    Recommendation: carry `from_line` and `to_line`, or the replaced
    text, and hold them against GitLab's; as optional, checked inputs
    that adds no break. Recorded in §16a, and the documents say what the
    prompt shows.
  - Unchanged in this range: `Invisible` lets a carriage return through
    anywhere, and the comparison keeps a lone one exactly; the argument
    carries it, so the model sees it, and how a client's prompt draws it
    is the client's.
- **`GITLAB_MCP_REQUIRE_PROMPT`** (`internal/config/config.go` `Build`,
  `RemovedVars`): no finding. Probed with a built binary: `serve` with
  `yes` or `maybe` exits 1 and `status` reports the configuration
  invalid; unset, empty, `0`, `false`, `no` and `off` start. The refusal
  does not echo the value, and `--require-prompt` is an unknown flag. The
  2.4.0 bundle manifest never passed the setting.
