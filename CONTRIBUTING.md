# Contributing

Thanks for looking. A few things here are not obvious.

## Before anything else

```bash
make hooks   # once: the pre-commit leak scan
make check
```

`make check` is the definition of done, and CI runs the same targets.
`make parity` holds the two equal, and `make checklist` holds `check`
against the list in `CLAUDE.md`. Every tool is fetched at a pinned
version through `go run`, so the Go toolchain is all you need.
`docs/development.md` says what each gate holds and why.

## Rules that are not style

A change that breaks one of these is sent back:

1. **Nothing from a real GitLab instance enters the repository.** No
   hostname, namespace or project path, branch, username, email address,
   title, comment, file path or contents, job log, numeric id,
   application id or token, in code, docs, fixtures, tests, commit
   messages or pull requests. Fixtures are generated by `gitlabtest`,
   never recorded. `make leaks`, `make secrets` and the pre-commit hook
   enforce the shapes they can see.
2. **Stdout carries only MCP JSON-RPC frames.** Logs use `slog` to
   stderr. `forbidigo` enforces it outside `main`.
3. **Logs never carry the payload.** Method, tool, outcome, duration
   and a truncated id only. A test drives every tool with canaries.
4. **Content is data, never instructions.** It is rendered inside
   marked boundaries, and no tool description tells the model to act on
   what content says.
5. **Nothing this server writes runs a quick action.** Every body goes
   through `internal/quickaction`; `make bodies` holds it.
6. **Ship and Destructive tools stay unregistered** unless their flags
   are set, and a create is never retried.

`CLAUDE.md` lists the rest, and `docs/architecture.md` explains them.

## Phases

Work follows the phases in `docs/architecture.md` §16. Each phase ends
with `make check` green, a live run whose transcript is read, and a
review, and then stops. The next phase starts only when the maintainer
says so; a tag is not that approval.

Ask before adding a scope, moving a tool between the Read, Write, Ship
and Destructive kinds, or reversing a decision §14 records.

## Changing the tool surface

The released tool surface is a contract. `make schema-diff` fails on a
removed tool, a lost field or a new required input. On a pull request,
a changed surface also needs an acknowledgment on a commit the pull
request adds, as an empty commit rather than an amend:

```bash
git commit --allow-empty -m "Acknowledge the tool surface change" \
  -m "SCHEMA-CHANGE: <what was added>"
```

Use `BREAKING CHANGE: <what breaks>` for anything that is not additive.

## Adding an API call

`make api-coverage` fails on a client call with no verdict. Add or update
the operation's row in `testdata/api-coverage.tsv`. `make api-fields`
fails on a field the published API does not have.

## Errors

Every error is `[class] message`, from the closed list in
`docs/architecture.md` §6.5. `make classes` holds the code and the list
equal both ways, so change them in the same commit.

## Commits and branches

`main` takes pull requests only. Work on a short topic branch, write a
message that says what and why, and add a CHANGELOG line under
`[Unreleased]` for anything a user would notice. Tagging is the
maintainer's; `docs/release.md` describes it.

## Reporting a bug

Use the issue template. It asks for `doctor` output, the version and a
debug log, all safe to paste. Do not paste a tool result, anything from
your instance, or a token.
